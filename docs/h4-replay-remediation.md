# H4 replay remediation and Gate 2 candidate

I make `h4_run SOURCE RECEIPT --replay` validate the complete receipt inside the bounded worker. It accepts an original envelope or a strict versioned wrapper. A bare ledger requires `--ledger-only`. The worker checks duplicate JSON members, canonical states, source and module bindings, gate and charge replay, outer metadata, size and phase decisions. It checks an included wrapper digest when present. A consistent envelope or a self-reported digest does not authenticate execution.

I leave the on-disk ledger decisions PASS and FAIL intact for historical compatibility. The H4 command reports VERIFIED_PASS with exit status 0, VERIFIED_BUDGET_EXCEEDED with status 1, INVALID_RECORD with status 2, and UNSUPPORTED with status 3. Automated acceptance gates must treat only exit status 0 as an accuracy-budget pass; a valid exceeded-budget receipt remains available for independent inspection. A verified budget excess refers to the certified upper bound. It does not establish a lower bound on actual error. An unsupported source request, such as an out-of-scope gate or overflowing generation, produces no receipt. An inconsistent recorded computation is invalid. I preserve the original H4 module-hash pair as an explicit compatibility case alongside exact current source binding. The old numeric ledger is still fully replayed. I leave all archived bytes intact.

## Differential reproduction

I run `python -B -m tools.high_support.h4_differential` and repeat with `-O` and `-OO`. The generator derives four exact words per index from SHA-256 of the fixed seed and decimal index. The five equally sized strata cover general finite encodings, edge encodings with both signs, nearly opposite operands, the overflow midpoint and its neighbors, and the normal/subnormal transition region. Each case compares a complex H pair in both engines, including exact output words or an overflow refusal. The output records the source hashes, canonical transcript hash and elapsed time. With `--words NEW.jsonl`, I can export all exact input and output words as decimal integers without overwriting any prior record. I compare repeated H, mixed gates, exact ideal prefixes and cumulative deletion charges separately in the ledger tests. This is a new independently seeded reproduction of the case count, not a claim that the audit's original generator or rows were identical.

## Narrow public candidate, pending review

I propose a separate opt-in version for finite, unnormalized X/Z/CX/H, with at most eight qubits and 64 gates. It accepts no scheduled deletions, normalization, or mixing-gate pruning. The entry point would take finite built-in binary64 real and imaginary components and encode each via big-endian `struct.pack(">d", value).hex()` after type and finiteness checks. It would preserve signed zeros and reject coercion from integers, decimals, arbitrary objects and nonfinite values. Wire and state ordering would be fixed. The source binding would cover the exact UTF-8 request, including the canonical words, ordered gates, contract version and nonnegative rational L2 budget.

I would reuse the historical coefficient and explicit nearest-even software operations, with gradual underflow and overflow refusal. For each gate I would independently replay bits and charges using a second engine, require zero deletion charge, and reproduce the cumulative upper bound and decision. I would keep the execution and replay resource bounds of the experimental path, including source and receipt caps, worker deadline and supported Windows/Linux process containment. I would require a versioned envelope, reject unknown fields and preserve the four outcome categories. I would use a separate mathematical-state hash and bit hash. Wrapper metadata would remain unauthenticated.

This design is not wired to the installed public interface. Before enabling it I need independent review of the conversion and canonical source format, compatibility/failure tests against the public entry point, explicit resource and outcome contracts, and finalized versioning. General sparse mixing, normalization and larger workloads remain out of scope. The public signed-permutation certificate stays unchanged.

## ARM64 observations

I recorded six runs in [the differential evidence](../evidence/h4-replay-remediation/differential.json). They reproduced the same transcript hash with zero mismatches. Across five Windows launches per mode, median wall time on the nine-gate fixture was 591 ms for complete receipt replay and 584 ms for explicit ledger-only replay. These measurements include process startup and containment, so I do not attribute the difference solely to metadata checks. The arithmetic sweep took roughly 84 to 85 seconds per Windows run and 59 to 61 seconds per WSL2 run.
